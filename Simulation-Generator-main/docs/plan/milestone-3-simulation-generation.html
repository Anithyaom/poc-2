Day 3 · am

The validation gate

validate_core asserts the handshake before anything is persisted: complete document, CSP present, every required message handled, all four transport messages when time_stepped, every approved id used verbatim, and no control UI of its own. A failure retries once with the specific problems fed back — grounded feedback, not self-critique.

The same seam injects the core's styles. Once the gate passes, inject_tokens deterministically writes a host-authored <style> block into the document's <head> — CSS custom properties for palette, type scale and spacing. The model is told to use the tokens; we guarantee they exist rather than hoping. Ships with a real, validated set — see §05 — so slice 6 becomes a CSS edit instead of a pipeline change, and every stored core is restyleable without regenerating it.

Day 4

Raise core ambition

Only once a real core renders. A 3.6k-token core uses 22% of the ceiling; a three-panel core with a plot is perhaps 8–10k and still fits. Populate the design tokens from slice 4, then push the contract toward linked views, plotted history and richer visual state — while holding the split: the shell owns every control, the core owns the scene.

The reference is a direction, not a benchmark. Take its region model and its one good instinct — colour that encodes data, as in Buffer Overflow's memory blocks. Reject the rest: decorative palettes that mean nothing across labs, red/green series encoding, walls of numbered instructions, containers nested four deep, and star ratings in the most valuable space on the page. The bar is "every simgen simulation feels like one product", which the reference structurally cannot claim — its six labs were hand-built separately and look it. Rules the contract enforces: never a hex literal, at most three tracked quantities, one axis and never two y-scales, recessive grid, and a visible label on every distinct element.

No external libraries, now or later. The CSP is default-src 'none', so there is no CDN and no fetch, and loosening it is a locked decision. Native platform covers more than it sounds: Canvas 2D, SVG, CSS Grid, the Web Animations API, and MathML for equations — natively supported in current Chrome, Safari and Firefox, so the Quantum sample's rendering needs no KaTeX. If plotting repetition becomes real, inject a ~2KB host-authored axes()/plot() helper through the slice 4 seam: it costs zero output tokens because we write it, not the model, and every chart then matches by construction.

Key code

The four places this goes wrong quietly: a cross-check that cries wolf, a gate that passes a broken core, a token block improvised by taste, and a retry that learns nothing from the failure.

backend/src/llm/coherence.py
_NUMBER = re.compile(r"-?\d+(?:\.\d+)?")

def check_coherence(plan: Plan) -> list[str]:
    """Numbers a rule names must be reachable from the control it names.

    Heuristic by necessity — prose is prose. It fires only when a rule mentions a
    control by label AND names numbers, so a vague rule is deliberately allowed
    through. A false positive here blocks a good blueprint, which is worse than
    the failure it prevents; bias hard toward silence.
    """
    problems: list[str] = []
    prose = [*plan.behavior_rules, plan.simulation_experience.initial_state]

    for control in plan.controls:
        if control.type not in ("slider", "number"):
            continue
        for line in prose:
            if control.label.lower() not in line.lower():
                continue
            values = [float(n) for n in _NUMBER.findall(line)]
            if _enumerates(line, values):
                problems.append(
                    f"{control.label!r} is offered as a {control.type}, but a rule "
                    f"lists set choices ({_fmt(values)}) — that means a dropdown."
                )
            elif outside := [v for v in values if not control.min <= v <= control.max]:
                problems.append(
                    f"{control.label!r} allows {control.min}–{control.max}, "
                    f"but a rule names {_fmt(outside)}."
                )
    return problems
backend/src/simulation/validate.py
_REQUIRED = ("sim:init", "sim:set", "sim:ready", "sim:readout")
_TRANSPORT = ("sim:play", "sim:pause", "sim:step", "sim:reset")
_OWN_UI = re.compile(r"<(button|input|select)\b", re.I)

def validate_core(core_html: str, manifest: Manifest) -> list[str]:
    """The shell/core contract, checked before anything is persisted."""
    problems: list[str] = []
    if not core_html.lstrip()[:15].lower().startswith("<!doctype html"):
        problems.append("not a complete HTML document")
    if "Content-Security-Policy" not in core_html:
        problems.append("the network-blocking CSP meta tag is missing")
    problems += [f"never handles {m}" for m in _REQUIRED if m not in core_html]
    if manifest.time_stepped:
        problems += [f"time-stepped but never handles {m}"
                     for m in _TRANSPORT if m not in core_html]
    if _OWN_UI.search(core_html):
        problems.append("draws its own controls — the shell owns every control")
    approved = [p.id for p in manifest.parameters] + [r.id for r in manifest.readouts]
    problems += [f"never uses approved id {i!r}" for i in approved if i not in core_html]
    return problems

The three series hues are the reference palette's first three slots, and they are the *validated* three — all-pairs CVD ΔE 9.2, normal-vision ΔE 24.0, both clear of the floors. The fourth slot would put yellow beside orange and fail. That is why the contract caps a core at three tracked quantities: past three, fold or facet. backend/src/tasks/simulation.py
def _generate_core(*, plan: Plan, manifest: Manifest) -> tuple[CoreOutput, dict]:
    """One attempt, then one retry — but the retry is told exactly what failed.

    This is the difference between a grounded loop and self-critique: the model
    never reviews its own code, it is handed a deterministic verdict on it.
    """
    user = sim_core_user_prompt(plan=plan, manifest=manifest)
    core, raw = structured_completion(
        system=SIM_CORE_CONTRACT, user=user, schema=CORE_SCHEMA,
        schema_name="simulation_core", model_cls=CoreOutput,
    )
    problems = validate_core(core.core_html, manifest)
    if not problems:
        return core, raw

    logger.warning("Core failed the gate, retrying once: %s", problems)
    core, raw = structured_completion(
        system=SIM_CORE_CONTRACT,
        user=f"{user}\n\nThe previous attempt was rejected:\n"
             + "\n".join(f"- {p}" for p in problems),
        schema=CORE_SCHEMA, schema_name="simulation_core", model_cls=CoreOutput,
    )
    if remaining := validate_core(core.core_html, manifest):
        raise LLMOutputError("; ".join(remaining), raw=core.core_html)
    return core, raw
06

Future scope

What this plan deliberately leaves alone, and the assumptions it makes that are worth contradicting during review.

The gate reads text; it does not run the simulation.

validate_core greps a string. It proves the core mentions sim:ready, not that it fires it; it cannot catch a sim that loads and then draws nothing. Actually executing the core needs a headless browser in the worker image — real weight for a POC. The teacher is the runtime check for now, which is consistent with the review-gate philosophy everywhere else in this pipeline. Worth revisiting if broken-but-valid cores turn out to be common rather than rare.

Assumption · revisit after ~10 real generations

Should the coherence check also run at acceptance?

As planned it runs in the generation task, so a model-authored blueprint is gated. But teachers hand-edit control ranges on the review screen, and accept_with_modifications writes that edit straight through — a human can introduce exactly the contradiction the check exists to catch. Running it on the decision endpoint too is cheap; the open question is whether it should block a teacher or merely warn them. Blocking a teacher from their own edit is a much harsher act than failing a model's output.

Decide with · owner · before slice 1 lands

Ambition is a prompt change, not an architecture change.

The reference screenshots draw their own panels, buttons and upload controls — which our split forbids. So “match that quality” means richer scenes: linked views, plotted history, annotated state. Every control still belongs to the shell. If a target sim genuinely needs an interaction the manifest cannot express, that is a signal about the parameter vocabulary, not a licence for the core to draw UI. Deliberately scheduled after a core renders, so ambition is tuned against something real.

Slice 6 · reassess against the sample set

The reference samples are not one design system, and one of them is out of reach.

All six screenshots are Virtual Labs (MoE) products sharing an outer platform frame — hamburger, logo, star rating, Rate Me. Inside that frame they are mutually inconsistent: different palettes, fonts, button shapes and input styles per lab. So matching them is not a design-system problem; our shell/core split can be considerably more consistent than the reference is.

The honest limit is assets. The IoT sample uses photographic component artwork — a Raspberry Pi board, a resistor, a phone. With img-src data: every asset must be inlined, and no model draws a recognisable Pi board in vector code. Matching that style needs a curated, domain-specific asset library, which is out of POC scope. The Blockchain, Linear Regression and Buffer Overflow styles — shapes, layout, text, canvas — are all reachable.

Assumption worth contradicting: the scene is light inside a dark shell, on the basis that the only POC viewer is a teacher on a laptop reviewing their own work, and the simulation should read as the bright object on the page. If these are ever projected in a classroom, that assumption changes the palette rather than decorating it — projectors crush mid-tones, and the tokens would need higher contrast, larger minimum type and thicker strokes.

Assumption · revisit if sims are ever projected, or if the asset pipeline is wanted

The transport bar may not survive as a flag at all.

The owner's position on first seeing it in the browser: the bar should show for every simulation, which would delete time_stepped from the schema, the prompt, the review screen and the manifest. That decision is deferred until real cores exist to judge it against — but it constrains this milestone in one way. Build nothing that assumes the flag is permanent: validate_core should read manifest.time_stepped once, and the workspace should never branch on it. If the flag becomes "always true", that must be a one-line change, not a refactor.

Handoff §5 item 8 · revisit after ~5 generated cores

The four ready labs are a flawed test set — deliberately.

Every lab currently in plan_accepted has time_stepped: false, because migration 0004 backfilled it and a migration must not guess from prose. Two of them — Binary Search: Halving the Hunt and What Sets a Pendulum's Period? — plainly do step. Generating from them as-is produces correct cores with no transport bar, which will look like this milestone's plumbing is broken when it is not. Flip the checkbox before the first test generation, or draft one fresh blueprint and use that as the day-3 smoke test.
