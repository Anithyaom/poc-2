01

Brief summary

Written in ASD-STE100 Simplified Technical English.

A teacher reads the blueprint. The teacher does not agree with one part of it. The teacher has only two controls: accept, or reject.

Reject is too strong. Reject sends the teacher back to the first screen. The teacher must then write the original description again. The teacher knew the correct change, but the system did not use that knowledge.

This plan adds a third control. The teacher writes the necessary change in a text box. The system sends the current blueprint and that text to the model. The model changes only the parts the teacher mentioned. The model keeps all other parts.

The work has five parts:

  1. Write a revision prompt. The prompt receives the current blueprint and the feedback.
  2. Add a revise_plan background task. Use the same shape as generate_plan.
  3. Add the route POST /api/plans/{id}/revisions. The route returns a job id.
  4. Add a Request changes button and a text box to the review screen.
  5. Test the complete path against the live model.

The teacher can also change sections by hand at the same time. The system saves those changes as a version first. The system then revises that version. The teacher does not have to choose between the two methods.

The database structure does not change. No version is overwritten. If the model fails, the teacher keeps the blueprint and keeps their own changes.

Milestones

Five slices, bottom-up. Slices 1–3 are testable from a terminal before any UI exists.

Slice 1

Revision prompt

plan_revision_user_prompt(plan, feedback, …) beside the existing plan_user_prompt. It reuses PLAN_SYSTEM_PROMPT unchanged, so every rule already in force — audience depth, authoring order, control coherence — still applies to the revision. try_plan.py gains --feedback so the prompt can be iterated with no stack, no database and no browser.

Slice 2

revise_plan task

Modelled line-for-line on generate_plan: mark running, call, validate, one retry, write the artifact, mark succeeded; a malformed response is a failed job with the raw text kept, never a crash. JobType gains REVISE_PLAN — a CharField value, so no migration.

backend/src/tasks/plan.py backend/src/job/models.py
Slice 3

Revisions route

POST /api/plans/{id}/revisions takes {feedback_text} and an optional edits, 409s if the source plan is not pending, and returns 202 {job_id}. When edits are present it first persists them as a new pending version and revises from that — so unsaved section edits and a feedback request can be sent together, and neither is lost if the model call fails. Same response contract as plan:generate, so the frontend's existing polling works unchanged.

backend/src/plan/router.py backend/src/plan/schemas.py
Slice 4

Request changes UI

A third button in the sticky action bar. Pressing it reveals one focused textarea — not a permanently visible form, matching how section editing already works. Submit sets jobId, so the existing useJob poll and the router.refresh() effect carry the teacher into the new version with no new fetch logic.

web/components/PlanWorkspace.tsx
Slice 5

Verify against the live model

Ruff, ESLint, tsc, production build. Then the real test: ask for one narrow change ("make the list size a dropdown of powers of two") and confirm the returned blueprint changed that and left the objective, visuals and rules intact. Then a failure case — confirm the original draft is still reviewable.

C · With unsaved edits — they come along

What should change?
Add a second graph showing comparisons against list size.
Your edits to What students can change will be kept and revised together with this request.
Revise blueprint

Edits and feedback are natural to want together — you fix a slider range yourself because it is quick and needs no model call, and ask for the graph because it does. The teacher is told their edits are included, not blocked.

D · What the version list shows afterwards

v2 Drafted by the model superseded
v3 Your edits, saved before the request superseded
v4 Revised from your feedback pending — under review

Nothing is lost in any branch. If the model call fails, v3 exists and is still reviewable — which is strictly better than today, where unsaved edits live only in React state and vanish on a refresh. Without edits, the sequence is simply v2 → v3 and no intermediate row is written.

06

Key code

Three places where the obvious implementation is the wrong one.

backend/src/plan/router.py — edits become a version before the model runs
# The teacher's own edits are persisted BEFORE dispatch, not carried
# in the task payload. If the model call fails they still exist as a
# reviewable row — today they live only in React state and a refresh
# destroys them.
source = plan
if payload.edits is not None:
    plan.decision = PlanDecision.SUPERSEDED
    await plan.save()
    source = await PlanVersion.create(
        lab_id=plan.lab_id,
        version=plan.version + 1,
        raw_llm_response=None,      # a human authored this one
        plan_json=payload.edits.model_dump(),
        decision=PlanDecision.PENDING,   # NOT accepted — review continues
    )

job = await GenerationJob.create(
    job_type=JobType.REVISE_PLAN,
    status=JobStatus.QUEUED,
    lab_id=plan.lab_id,
    target_id=source.id,   # what the revision is based on
)

PENDING is the load-bearing word. The existing accept_with_modifications path writes an edited row as ACCEPTED and ends the review; here the identical write must leave the review open, or asking for changes would silently approve the blueprint.

backend/src/tasks/plan.py — write first, supersede second
# Order matters. If the model fails, the teacher must still have a
# reviewable draft — so the source row is only retired once its
# replacement exists. Never mark superseded before the create.
revised = await PlanVersion.create(
    lab_id=lab.id,
    version=source.version + 1,
    raw_llm_response=raw,
    plan_json=plan.model_dump(),
    decision=PlanDecision.PENDING,
)
source.decision = PlanDecision.SUPERSEDED
await source.save()

# lab.status stays PLAN_REVIEW and active_plan_id is untouched —
# only an acceptance points the lab at a plan.
backend/src/llm/prompts.py — the preservation instruction
def plan_revision_user_prompt(*, plan, feedback, audience, course_title, course_subject):
    """Revise an existing blueprint. Same system prompt, same schema."""
    return (
        f"Course: {course_title} ({course_subject})\nAudience: {audience}\n\n"
        "This simulation blueprint was drafted for the teacher, who has "
        "asked for changes:\n\n"
        f"{json.dumps(plan, indent=2)}\n\n"
        f"The teacher's words:\n\n{feedback.strip()}\n\n"
        "Return the COMPLETE blueprint with their request applied. Change "
        "only what they asked about and what must follow from it — if a "
        "control changes, the behavior rules and expected observations that "
        "mention it must change with it. Everything they did not raise must "
        "come back word for word. Do not re-word, re-order, improve, or "
        "re-title anything they did not mention."
    )

The second half of that instruction is the load-bearing part. "Preserve everything not mentioned" alone invites the model to quietly re-word prose it thinks it can improve, and the teacher then has to re-read a document they had already approved. But a control change genuinely must propagate into the rules and observations that reference it — so the instruction has to permit consequential edits while forbidding cosmetic ones.

07

Future scope

Assumptions I made without asking, and one decision worth taking at review.

Should the feedback text be stored?

Assumed no — the POC keeps it only in the prompt. But version history then shows that v3 replaced v2 without showing why, which is exactly the question append-only versioning exists to answer, and it is the first thing you will want when a revision goes wrong. A nullable revision_feedback text column on plan_versions would fix it for one reviewed migration. I would take it now; it gets more expensive once there are rows worth explaining.

Decide at plan review · costs one migration

A revision with edits writes two rows, not one

Accepted as the cost of losing nothing. A teacher who edits and asks for changes three times produces six versions, and the history list will read as noisier than the number of decisions they actually made. If that becomes uncomfortable, the fix is presentational — collapse a human-authored row and the revision that consumed it into one history entry — not a change to what gets written. Never merge them at the storage layer; the whole guarantee is that the edit survives a failed model call.

Presentational fix if history gets noisy

Reject should get quieter once this ships

Reject and redraft throws away the blueprint and returns the teacher to their original prose; the regeneration never sees what was rejected or why. That stays the right action for a genuinely misread request — wrong topic, wrong concept, wrong level — but it stops being the normal one. Worth demoting it visually in slice 4 so Request changes reads as the default response to "this isn't right yet".

Fold into slice 4

Ambiguous feedback has no clarification path

"Make it better" will produce something, because the schema forces a complete blueprint. Call #3 solves this properly with an outcome discriminator that lets the model ask a question instead of guessing (spec §6). Worth copying here once call #3 exists — not worth designing twice.

After milestone 4

No limit on revision rounds

A teacher can revise indefinitely, and each round is a real model call and a new row. Fine for a demo, and the version list makes the cost visible. Worth a look only if a blueprint reaches double-digit versions in practice.

Not a POC concern

Deliberately out of scope

Transport-bar plumbing (time_stepped) and the control-versus-rules coherence validator are both still queued ahead of milestone 3. Neither touches this work, and mixing them in would make one approval cover three unrelated changes.
